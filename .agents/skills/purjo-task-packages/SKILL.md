# Purjo task packages

Use this skill when working on a Robot Framework (or pure Python) package
executed by an Operaton external service task. `purjo` (CLI: `pur`, also
aliased `purjo`) is an experimental tool that uses `uv` to run isolated Robot
Framework environments, long-polls Operaton, maps BPMN topics to Robot tasks,
and reports task results and output variables.

Vocabulary: say *Operaton* (not Camunda), *robot package* (not robot.zip),
*external task* (not job).

## Package contract

A package is a directory containing:

- `pyproject.toml` with runtime dependencies and `[tool.purjo.topics]`
- one or more `.robot` suites using `*** Tasks ***` (or `*** Test Cases ***`),
  or a pure-Python module (experimental, see below)
- `.wrapignore` for files excluded from `pur wrap`
- `uv.lock`, generated by `uv`, not edited by hand
- optionally a `Makefile`, README, and `AGENTS.md`

Each topic mapping must match the BPMN external task exactly:

```toml
[tool.purjo.topics."Topic in BPMN"]
name = "Task name in Robot"
on-fail = "ERROR"
process-variables = true
pythonpath = ["./libs", "./modules"]
```

- The topic key must equal `camunda:topic` on the BPMN service task.
- `name` must equal the Robot task/test name character-for-character (or, for
  a pure-Python task, the `module.function` to run).
- `on-fail` is `ERROR` (raises a catchable BPMN error), `FAIL` (engine task
  failure, consumes a retry), or `COMPLETE` (completes anyway with
  `errorCode`/`errorMessage` as output variables). CLI default is `FAIL`.
- `process-variables`: `true` passes all process variables to the
  task/test; `false` passes only task-scope variables.
- `pythonpath`: optional list of extra directories added to Robot's
  `--pythonpath`.

When failing deliberately, put the **error code** on the first line and the
**error message** on the rest:

```robotframework
${errorCodeAndMessage}=    Catenate    SEPARATOR=\n
...    Bad luck
...    You rolled ${dice}, which is less than ${threshold}.
Fail    ${errorCodeAndMessage}
```

## Create and develop

Initialize a task package with:

```console
uv run --with=purjo -- pur init --task --agents
```

- `--task` uses `*** Tasks ***`/`Task Template`/`Run Robot Task` instead of
  the default `*** Test Cases ***`/`Test Template`/`Run Robot Test`.
- `--agents` also generates a project `AGENTS.md` tailored to the chosen
  flavour; it is wrapignored, developer-facing only.
- `--python` generates an experimental pure-Python template instead
  (adds `purjo` as a dev dependency for `PythonParser`, defaults
  `on-fail = "FAIL"`); not supported together with `--agents`.

Use `uv add` for runtime dependencies and `uv add --dev` for test-only
dependencies (`robotframework-robotlibrary>=1.0a3` for integration tests,
`purjo` itself for functional tests — see Testing below). Run `uv lock`
after dependency changes.

Inputs arrive as normal Robot suite variables and must be declared with a
default under `*** Variables ***`; undeclared variables are not available to
the task. Use list/dict sigils for structured variables, e.g. `@{List Input}`
and `&{Dict Input}    &{EMPTY}`. Purjo converts common BPMN types (string,
number, boolean, date, list, dict) to Python/Robot values automatically.

Keep `${BPMN:PROCESS}    local` in the suite variables — it lets local
integration tests override the process scope (see Testing). Emit outputs
with Robot's built-in `VAR` keyword:

```robotframework
VAR    ${result}    ${value}    scope=${BPMN:PROCESS}
```

Use `scope=${BPMN:TASK}` for values local to the current external task only.

### Pure Python tasks (experimental)

A task can also be a plain Python function instead of a `.robot` suite, using
`purjo.PythonParser`:

```python
from pydantic import BaseModel
from robot.libraries import BuiltIn

class InputVariables(BaseModel):
    name: str = "John Doe"

class OutputVariables(BaseModel):
    message: str

def main():
    variables = InputVariables(**BuiltIn.BuiltIn().get_variables(no_decoration=True))
    result = OutputVariables(message=f"Hello, {variables.name}!")
    for name, value in result.model_dump().items():
        BuiltIn.BuiltIn()._variables.set_bpmn_process(f"${{{name}}}", value)

if __name__ == "__main__":
    from purjo import PythonParser
    from robot import run
    run(__file__, parser=PythonParser("tasks.main"))
```

Map it with `name = "tasks.main"` (a `module.function` path) in
`[tool.purjo.topics]` instead of a Robot task name.

### Secrets

Secrets are injected variables, not files. Configure a profile in
`pyproject.toml`:

```toml
[tool.purjo.secrets.default]
provider = "file"
path = "secrets.json"

[tool.purjo.secrets.prod]
provider = "vault"
path = "secret/my-app"
mount-point = "secret"
```

A relative `file` path is resolved against the package directory (so `pur
serve` finds it regardless of cwd for a directory package; for a zipped
package it resolves against the working directory instead, since the zip
isn't extracted until a task runs). The `vault` provider needs `VAULT_ADDR`
and `VAULT_TOKEN` in the environment.

Select a profile with `pur serve --secrets prod .`, or point at a file
directly with `pur serve --secrets ./my-secrets.json .`. `pur wrap` never
packages a root `secrets.json`, and `pur serve` never copies it into a task's
sandbox — only a secrets file under another name or in a subdirectory would
be packaged like any other file.

Keep `secrets.json` untracked and provide a safe example file. With
`robotframework` >= 7.4b2, secret values arrive as `Secret` objects that mask
themselves in logs — read the underlying string as `${NAME.value}`. Never
emit secrets as BPMN output variables.

## Testing

Both styles below run locally with no BPM engine involved.

**Integration tests** — `robotframework-robotlibrary`'s `Run Robot Test` /
`Run Robot Task` keywords execute a task/test from another `.robot` file,
passing `NAME=value` overrides for its suite variables (or `&{dict}` expanded
as `&{inputs}`). Override `BPMN:PROCESS=global` so `VAR ... scope=${BPMN:PROCESS}`
writes to a scope the calling suite can assert:

```robotframework
*** Settings ***
Library             RobotLibrary
Test Template        Test Hello

*** Test Cases ***    NAME
Hello John    John Doe

*** Keywords ***
Test Hello
    [Arguments]    ${name}
    Run Robot Test    ${CURDIR}/hello.robot    My Test in Robot
    ...    BPMN:PROCESS=global    name=${name}
    Should Be Equal    ${message}    Hello ${name}!
```

**Functional tests** — the `purjo` Robot Framework library's `Get Output
Variables` keyword executes a configured topic the way the engine would, and
returns the output variables (or `errorCode`/`errorMessage` on failure) as a
dictionary. Use it to verify the `[tool.purjo.topics]` mapping, variable
conversion, `on-fail` behavior, and secrets handling:

```robotframework
*** Settings ***
Library    purjo
Library    Collections

*** Test Cases ***
Test My Topic
    &{inputs}=    Create Dictionary    name=Alice
    &{outputs}=    Get Output Variables    path=.    topic=My Topic in BPMN
    ...    variables=${inputs}    secrets=${secrets_dict}
    Should Be Equal    ${outputs}[message]    Hello Alice!
```

`path` is a directory with `pyproject.toml` or a `robot.zip`. Both testing
styles come pre-wired by `pur init` (`test_hello.robot` plus the
`robotframework-robotlibrary` dev dependency); add `purjo` as a dev
dependency to use `Get Output Variables`.

## Package, deploy, and serve

```console
make help                         # list Makefile targets
make test                         # uv run --group dev robot test_hello.robot
make dist                         # test, then pur wrap
make deploy                       # pur operaton deploy <files>
make serve                        # deploy, then pur serve .
make run                          # pur run <files>, then pur serve .

pur wrap                          # build robot.zip
pur wrap --offline                # ... with uv-cached dependencies bundled in
pur serve .                       # directory package
pur serve robot.zip               # wrapped package
pur operaton create process.bpmn  # new .bpmn/.dmn/.form with fresh IDs
pur operaton deploy process.bpmn  # deploy without starting an instance
pur operaton start <process-key>  # start an instance from an existing deployment
pur run process.bpmn              # deploy + start in one step
```

Configure the engine with `ENGINE_REST_BASE_URL` and
`ENGINE_REST_AUTHORIZATION`, or pass `--base-url` and `--authorization`.
`pur run`/`pur operaton deploy` also take `--name` (deployment name),
`--variables` (JSON string or file, `pur run` only), `--migrate/--no-migrate`
(migrate existing instances to the new version, default on), and `--force`
(deploy even if resources are unchanged). `pur serve` supports `--secrets`,
`--timeout`, `--poll-ttl`, `--lock-ttl`, `--max-jobs`, `--worker-id`, and
`--on-fail`.

Edit `.bpmn`/`.dmn`/`.form` files with a bpmn.io-compatible modeler, or
create them with `pur operaton create` — hand-editing the XML breaks diagram
references. Don't commit `secrets.json`, `robot.zip`, `.venv`, or Robot's
`output.xml`/`log.html`/`report.html`; keep files that shouldn't ship in the
package listed in `.wrapignore`.

## Migrating RCC packages

Replace `robot.yaml` topic mappings with `[tool.purjo.topics]`, and replace
`conda.yaml` dependencies with PEP 621 dependencies managed by `uv`. Remove
RCC Work Items and Vault APIs:

- inputs are already present as suite variables; do not call
  `Set task variables from work item`
- use `VAR ... scope=${BPMN:PROCESS}` for outputs instead of creating/saving
  work items
- configure Purjo secrets and read injected variables directly
  (`${NAME.value}` once `robotframework` >= 7.4b2 masks them), replacing
  `RPA.Robocorp.Vault`'s `Get Secret`
- replace work-item files with ordinary URLs or serialized variables; download
  binary content in the consuming task when needed

Verify every topic against the BPMN files before wrapping. Do not package
secret files, generated reports, or process resources unless intentionally
needed by the worker.
